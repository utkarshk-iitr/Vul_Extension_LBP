\chapter{Introduction}
\label{ch:introduction}

Software vulnerabilities pose a significant threat to modern application security. As software systems grow in complexity, are deployed in heterogeneous environments, and integrate hundreds of third-party dependencies, security assurance becomes a continuous challenge. Vulnerabilities are no longer isolated defects; they can rapidly propagate through supply chains and compromise downstream systems. As a result, early and automated vulnerability detection is essential to reduce risk and minimize remediation cost.

In practice, secure development is constrained by time, scale, and the human cost of analysis. Large organizations handle extensive codebases and rapid release cycles, where manual auditing is impractical. Traditional static analysis tools provide broad coverage but often produce high false positive rates and lack semantic understanding of code context. This generates alert fatigue, weak prioritization, and slower remediation cycles. Conversely, dynamic analysis and fuzzing can be effective but require runtime environments, configuration effort, and significant compute, which makes them difficult to run for every change.

Learning-based approaches show strong promise for vulnerability detection by capturing semantic and structural cues from code. However, many state-of-the-art models remain research prototypes: they are run offline, require custom pipelines, and provide outputs that are difficult for developers to interpret or act upon. The result is a gap between model capability and real-world usability. To be effective in practice, detection must be fast, explainable, and integrated into the tools developers use daily, with workflows that minimize context switching and provide actionable guidance.

VulGuard addresses these challenges by embedding model-backed vulnerability detection directly inside Visual Studio Code. The extension reads source code from the active editor, sends it to a persistent inference server, and returns localized findings in near real time. It highlights vulnerable lines, summarizes risk, and surfaces structured fix suggestions generated by LLMs with retrieval-augmented context. This design supports both rapid triage and iterative remediation without leaving the IDE. By combining practical UX with advanced analysis, VulGuard bridges the gap between research-grade models and day-to-day software engineering.

Modern development workflows also demand traceability and explainability. Teams must understand why a piece of code is flagged and how a proposed fix changes behavior, especially in critical systems. Pure classification outputs are insufficient when security engineers must justify risk to stakeholders or ensure that a fix does not introduce regressions. VulGuard therefore prioritizes line-level localization, contextual explanations, and reviewable patch candidates that developers can inspect and approve.

Another constraint is the heterogeneity of real-world code. Projects mix legacy code with modern frameworks, employ diverse coding styles, and evolve rapidly. A useful system must generalize across projects while remaining responsive to project-specific patterns. By combining model inference with retrieval-augmented context and by keeping inference servers warm for fast responses, VulGuard aims to provide consistent, low-latency feedback that scales with team size and codebase size.

Finally, security tools must integrate into existing practices rather than replace them. Developers rely on IDEs, code review, and continuous integration pipelines, and any additional process overhead reduces adoption. VulGuard is built to fit into these workflows by offering lightweight, on-demand analysis inside the editor, enabling quick triage during development and reducing the time between discovery and remediation.

\chapter{Related Work}
\label{ch:related-work}

In recent years, the combination of machine learning and software security has seen significant progress. The following works are directly relevant to VulGuard and motivate our design choices.

\section{VulExplainer}
VulExplainer proposes a transformer-based hierarchical distillation approach for generating human-readable vulnerability explanations \cite{vulexplainer}. Its emphasis on explanation quality aligns with our goal of developer-friendly reporting and reduces the burden of manual triage. We set up the authors code locally and verified their explanation generation on a small subset of test cases, confirming the claims of model.

\section{VulRepair}
VulRepair frames vulnerability fixing as a sequence-to-sequence repair task using T5-style models \cite{vulrepair}. This work demonstrates that automated repairs can be synthesized from vulnerable code and that patches can be generated at scale. We set up and tested the open-source implementation locally and validated multiple repair outputs against reported behavior.

\section{VulDeePecker}
VulDeePecker introduces a deep learning-based pipeline for detecting software vulnerabilities from code gadgets \cite{vuldeepecker}. It established the utility of neural representations for vulnerability detection and highlighted the importance of curated training data for robust performance. The gadget-based framing also informs how vulnerable contexts can be isolated from larger functions.

\section{GRACE} \vspace{-1em}
GRACE combines graph learning with context-aware modeling to improve detection accuracy \cite{grace}. The method demonstrates how context fusion can enhance classification beyond local patterns, supporting our focus on retrieval-augmented context for fix generation.

\section{Russell et al.} \vspace{-1em}
Russell et al. explore deep representation learning for vulnerability detection at the function level \cite{russell2018}. Their work demonstrates that learned features can outperform manual rule sets, particularly in noisy real-world code. The study reinforces the need for representations that generalize across projects and coding styles.

\section{SySeVR} \vspace{-1em}
SySeVR proposes a syntax-based, semantics-aware representation for vulnerability detection \cite{sysevr}. By combining syntax patterns with semantic relations, it improves model sensitivity to vulnerable code constructs. This motivates our emphasis on context-aware signals rather than purely lexical cues.

\section{REVEAL} \vspace{-1em}
REVEAL uses graph neural networks over code property graphs for vulnerability identification \cite{reveal}. This graph-centric approach informs our consideration of structural cues during detection and explanation, especially for capturing data flow and control flow dependencies that are difficult to model with linear token sequences.

\section{Devign} \vspace{-1em}
Devign models code as a graph and applies gated graph neural networks for detection \cite{devign}. Its effectiveness reinforces the value of graph-based representations for capturing control and data flow, and it demonstrates that structured program analysis can complement learned embeddings.

\section{LineVul} \vspace{-1em}
LineVul provides line-level vulnerability localization \cite{linevul}. This directly informs our line highlighting strategy and supports actionable findings in the editor. Its localization ability also motivates reporting precise, developer-friendly patches rather than coarse function-level flags.

\chapter{Motivation}
\label{ch:motivation}

One of the main challenges in software security is delivering accurate, actionable vulnerability findings within real-world development workflows. Although prior research has produced strong detection models, several shortcomings remain in practical usage. These gaps motivate our effort to build a more usable and reliable end-to-end solution.

\begin{itemize}
    \item \textbf{Limitations of traditional approaches:} Many tools depend on lexical patterns or shallow features (e.g., bag-of-words or heuristic rules) that miss semantic and contextual cues. This leads to missed vulnerabilities when subtle control-flow or data-flow issues are present and to false positives when safe code resembles known patterns.
    \item \textbf{Noisy, heterogeneous codebases:} Real projects mix legacy modules, varying coding styles, and diverse dependency stacks. Models trained on curated datasets often struggle to generalize across these conditions, which degrades detection quality in production settings.
    \item \textbf{Fragmented workflows:} Research prototypes frequently run outside the IDE, forcing developers to context switch, export code, and interpret raw logs without guidance. This friction reduces adoption and delays remediation.
    \item \textbf{Coarse-grained outputs:} Function-level alerts without line localization slow remediation and complicate code review. Developers must manually search for the actual root cause, increasing time-to-fix.
    \item \textbf{Weak explanations and fixes:} Many systems provide scores without reasoning, and automated fixes can be unsafe without grounded context. A practical tool must explain why a line is vulnerable and propose changes that respect surrounding code semantics.
    \item \textbf{Latency and scalability constraints:} Heavy pipelines or cold-start inference discourage frequent use during iterative development. Teams need fast, repeatable analysis that scales with file size and team velocity.
\end{itemize}

\chapter{Proposed Method}
\label{ch:proposed-method}

This chapter presents the VulGuard pipeline for vulnerability detection, explanation, and fix generation inside Visual Studio Code. Our method combines model-backed inference, retrieval-augmented context, and a review-first patch workflow to support fast and reliable remediation. The overall process is organized into the following phases.

\section{Method Phases}
\begin{itemize}
    \item \textbf{Phase 1: Input capture and preprocessing.} The extension reads the active editor buffer, canonicalizes line endings, strips transient editor markers, and computes a content hash. The snapshot is stored with a revision token to ensure findings map to the correct file state.
    \item \textbf{Phase 2: Model inference.} The snapshot is serialized to JSON and sent to the inference server. The server performs tokenization and model forward passes, returning per-line vulnerability scores and a ranked candidate list.
    \item \textbf{Phase 3: Evidence enrichment.} When enabled, a bounded context window is extracted around each candidate line. Optional static-rule findings are merged and deduplicated. Evidence snippets are scored by proximity and relevance to stabilize LLM grounding.
    \item \textbf{Phase 4: Explanation and fix generation.} A structured prompt is assembled with the finding, evidence, and constrained output schema. The LLM generates explanations and multiple patch candidates, which are validated for syntax and minimal diff size.
    \item \textbf{Phase 5: Review and application.} Candidates are ranked and shown for explicit approval. The selected patch is applied using an editor edit, and the analysis can be re-run to verify that the vulnerability is removed.
\end{itemize}

Each phase is implemented as a bounded step with explicit timeouts and configuration flags in the extension settings. This allows the user to disable optional stages (such as RAG or LLM generation) while keeping line-level detection active. The phases are also designed to be incremental: if a prior run exists, VulGuard reuses cached artifacts (e.g., recent findings and evidence windows) to reduce latency.

\section{System Architecture and Capabilities}
The system has two primary components: the VS Code extension (front end) and a persistent Python inference server (back end). When a developer triggers analysis, the extension sends the active C/C++ file to the server, which runs a line-level vulnerability model (e.g., LineVul or a similar architecture) to produce localized findings and severity estimates. Results are returned to the editor as inline highlights with a summarized risk indicator.

The extension communicates with the server over a lightweight JSON protocol that includes the file path, content hash, and requested analysis mode. The server validates the request, executes the model, and returns a structured response containing per-line scores, vulnerable line indices, and optional metadata for downstream stages. This separation ensures the IDE remains responsive while the server handles compute-heavy inference.

\section{Retrieval-Augmented Generation and Fix Suggestion}
After vulnerabilities are detected, VulGuard enables a fix workflow through the "Apply Suggested Fix" command. Developers select a specific finding, and the extension assembles a structured prompt using retrieval-augmented context (neighboring lines, evidence snippets, and prior findings). This prompt is sent to a configured LLM provider (local Ollama or a cloud endpoint), which returns multiple patch candidates. VulGuard then presents these candidates for human review, and only applies a patch after explicit approval.

The RAG stage enforces a bounded context window around each vulnerable line and respects a configurable token budget. Evidence snippets are deduplicated and ordered by proximity and relevance. This grounding step reduces hallucinations and helps the LLM maintain semantic consistency with the surrounding code. Patch candidates are ranked using simple heuristics (e.g., minimal diff size and syntax validity) before being shown to the user.

\begin{algorithm}[htbp]
\caption{End-to-End VulGuard Analysis Pipeline}
\begin{algorithmic}[1]
\Require Active file content $C$, settings $S$, timeout $T$
\Ensure Findings $F$, patches $P$, content hash $h$
\State $C_{norm} \leftarrow \text{Normalize}(C)$
\State $h \leftarrow \text{SHA256}(C_{norm})$
\State $req \leftarrow \{C_{norm}, h, S.mode, S.model\}$
\State $resp \leftarrow \text{SendToServer}(req, T)$
\State $scores \leftarrow resp.lineScores$
\State $F \leftarrow \text{SelectTopK}(scores, S.topK)$
\State $F \leftarrow \text{ApplyThreshold}(F, S.thresh)$
\State $F \leftarrow \text{AttachLineContext}(F, C_{norm}, S.window)$
\If{$S.rag$}
    \State $E \leftarrow \text{BuildEvidence}(F, C_{norm}, S.ragWindow, S.ragTopK)$
\Else
    \State $E \leftarrow \varnothing$
\EndIf
\If{$S.llm$}
    \State $P \leftarrow \text{SynthesizePatches}(F, E, S.llm)$
    \State $P \leftarrow \text{ValidateAndRank}(P, C_{norm})$
\Else
    \State $P \leftarrow \varnothing$
\EndIf
\State \Return $F, P, h$
\end{algorithmic}
\end{algorithm}

\section{Operational Modes and Responsiveness}
To support different deployment environments, VulGuard runs inference either locally or via SSH. A persistent server avoids cold starts and keeps caches warm, enabling near real-time feedback during development. This design reduces latency and supports continuous use within standard IDE workflows.

When running in SSH mode, the extension transfers the analysis payload to the remote host and validates the response schema before applying highlights. In local mode, the extension can auto-start the inference server and reuse the same process across analyses. Both modes implement timeouts and retry logic to prevent blocking the editor.

\begin{algorithm}[htbp]
\caption{RAG-LLM Patch Synthesis}
\begin{algorithmic}[1]
\Require Finding $f$, code $C_{norm}$, evidence set $E$, model settings $S$
\Ensure Candidate patches $P$
\State $W \leftarrow \text{ExtractWindow}(C_{norm}, f.line, S.window)$
\State $E' \leftarrow \text{RankEvidence}(E, f, S.ragTopK)$
\State $ctx \leftarrow \text{AssembleContext}(W, f, E', S.budget)$
\State $schema \leftarrow \text{PatchSchema}()$
\State $prompt \leftarrow \text{ComposePrompt}(ctx, schema, S.style)$
\State $raw \leftarrow \text{LLMGenerate}(prompt, S.temperature, S.timeout)$
\State $P \leftarrow \text{ParsePatches}(raw)$
\State $P \leftarrow \text{FilterBySyntax}(P, C_{norm})$
\State $P \leftarrow \text{FilterByDiffSize}(P, S.maxDiff)$
\State $P \leftarrow \text{RankCandidates}(P, \{\text{minDiff}, \text{contextMatch}\})$
\State \Return $P$
\end{algorithmic}
\end{algorithm}

\chapter{Conclusion}
\label{ch:conclusion}

In this report, we presented VulGuard, a comprehensive vulnerability detection and resolution extension designed for Visual Studio Code. The extension leverages the capabilities of deep learning code analysis models and pairs them with local or cloud-based Large Language Models to offer immediate, actionable security feedback. By integrating features such as persistent inference servers, RAG-based context enrichment, and an automated patch generation mechanism within a standard developer workflow, VulGuard effectively addresses the limitations of detached security tools. This work demonstrates the practical viability of bringing state-of-the-art vulnerability analysis directly into the IDE, ultimately fostering the development of more secure software systems while preserving developer productivity.
